# Metric inventory (#992)

Every family the Login (`:9464/metrics`) and Zone (`:9465/metrics`) processes serve is listed here: what it means, its
unit, the process that serves it, the instrument in `src/Fineage.Protocol/Telemetry/FineageTelemetry.cs` that feeds it
(or where a scrape-time family is read), the code that records it, and the tests that prove it.

This file is checked by `tests/Fineage.Zone.Tests/MetricInventoryTests.cs`:

- `Every_recorded_instrument_moves_the_families_the_inventory_names` records one measurement into **every**
  `FineageTelemetry` instrument (an observable gauge gets a non-zero source through the hook production sets) and
  fails when an instrument has no row here or when a family named for it did not change in the scrape. A metric that
  is recorded but never exported, the #992 failure, cannot come back silently.
- `Every_exported_family_is_in_the_inventory_for_its_process` renders the Zone and the Login scrape and requires the
  set of families to equal the rows for that process, in both directions.
- `Alerts_and_dashboard_read_only_inventoried_metrics_and_every_alert_metric_has_a_test` reads
  `monitoring/prometheus/rules/*.yml` and `monitoring/grafana/dashboards/*.json`: every metric they read must be a row
  here, and every metric a rule reads must name at least one existing test in **Verified by**.

How to read the table:

- **Process** is `zone`, `login` or both. The Login process no longer serves the zone simulation families as constant
  zeros; it serves the common network, persist-write, health, process and GC families.
- **Instrument** `—` means the family is computed at scrape time, not from a meter instrument; **Source** names what
  it reads.
- Histograms have `_bucket{le}`, `_sum` and `_count` samples. A per-endpoint family (`endpoint` label) and a histogram
  appear after the first measurement; a counter with labels appears with its first labelled series. Alert rules on
  such counters compare the cumulative value (`> 0`), not `increase()`, so the first event fires the alert.
- The collector only sees measurements made after it starts. Zone starts `/metrics` before the boot (#992), so the
  startup state audit, the startup reconcile and silent data fallbacks are counted and a booting zone scrapes as not
  ready; before #992 they were recorded before the listener existed and never reached `/metrics`.
- Counters are cumulative since process start; a restart resets them (Prometheus `rate`/`increase` handle that).
- `fineage_packets_per_second` is the frame rate since the previous scrape by **any** client (load-test tool or
  Prometheus). Dashboards use `rate(fineage_frames_in_total[1m])` instead.
- Removed in #992: `fineage.tick.stage.regions` (recorded every step, never exported or read) and
  `fineage.packets.per_second` (an observable gauge nobody exported; the summary loop and the scrape overwrote each
  other's window).

Debug load-run evidence (before/after scrape of a `bots-economy-hammer` run) is in the #992 pull request.
